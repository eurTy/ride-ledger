# 安卓点对点与多链路同步可行性验证

评估日期：2026-11-05。目标是 Android 10 及以上手机之间通信，电脑仅作过渡与模拟。现有最低版本仍保持 Android 8.0，不在此试验中调整。iOS 继续暂停。本分支是验证代码，未修改当前安装的 v0.1.4 APK/EXE，尚未将蓝牙或 Wi-Fi Direct 接入产品。

结论：同热点下无主账本的对等同步可在现有基础上扩展；不手动建立热点的近距离通信可选经典蓝牙 RFCOMM、Wi-Fi Direct。推荐共用一套本地操作日志与增量同步协议，再实现不同连接适配器。多人支持需要独立改造成员和分摊模型；mesh 拓扑本身不会改变当前两人账本。

## 已实际验证的内容

`npm run test:mesh`：10 项通过、0 项失败。

| 范围 | 试验与结果 | 不能据此推断的内容 |
| --- | --- | --- |
| 现有实际 TCP 实现 | 3 个副本按 A—B—C 连接，无 A—C 连接时最终获得相同流水 | 未验证安卓的无线发现或物理传输 |
| 存储后转发 | A 退出后，B 仍能把已保存的 A 记录交给 C | 不能在完全没有连接路径时实时传递 |
| 4 节点环形 | 重复传播不重复计账，旧快照不能恢复已删除流水 | 未测无线干扰、后台限制与功耗 |
| 设备退出与重开 | 剩余设备继续交换，新记录可补到重开的旧副本 | 未证明热点提供者退出后原 Wi-Fi 网络仍存在 |
| 三成员原型 | 原始资金分别计算，共同支出精确分配到分，还款和换汇按币种守恒 | 未实现安卓多人界面、迁移或成员管理协议 |
| 多链路投递模拟 | 同一加密记录重复到达、回执丢失后重试只入账一次 | 没有运行蓝牙或 Wi-Fi Direct 适配器 |
| 乱序和删除 | 作者序号存在空洞时仍能找回漏项；删除先到不会让后到的原记录生效 | 尚无长期压缩和删除标记回收机制 |
| 时钟偏差与分区 | 不同录入时间和送达顺序最终得到相同账目 | 没有实现对同一记录的并发编辑 |
| 错密钥与冲突 | 错密钥、跨旅行、同 ID 不同内容被拒绝，整批校验失败不部分提交 | 原型没有设备签名与成员撤销，不具备完整多人授权机制 |
| 增量大小 | 200 条历史记录再新增 1 条时，只传新增记录正文，并计入双方摘要索引成本 | JSON 字节数不是实测无线流量、速度或电量 |

前四项使用实际 `desktop/lan-sync.mjs` TCP 帧、`web/app.js` AES-GCM 和流水合并代码，在隔离的本机地址和临时端口执行，关闭 mDNS 广播。每个测试明确控制连接拓扑和调度。它们验证的是当前两人账本的**多个设备副本**，不会将三设备说成已支持三个人记账，也不以测试调度时间代表正式客户端的 10/15 秒同步周期。

其余用例使用 `operation-log.mjs` 独立原型，未接入正式客户端。原型密文使用单独的实验协议域及版本 2 标记，不能与旧版互相冒充。身份签名、邀请授权、成员变动同步、撤销和正式输入限额仍需设计。

本次差分样本的应用层 JSON 大小：

| 内容 | 字节 |
| --- | ---: |
| 单条新增记录的加密封包 | 807 |
| 双方完整事件摘要索引合计 | 42,652 |
| 增量加摘要索引合计 | 43,459 |
| 对照：双方发送完整加密历史 | 275,875 |

这组特定数据的应用载荷约减少 84%，包含摘要索引成本，不含无线、操作系统和握手开销。原型仍发送随历史增长的 ID/哈希索引；生产实现宜先比较缓存的根摘要，不一致时再按桶或缺失区间交换索引，历史大时不能永远逐条列举。

完整结果与 TAP 日志由脚本生成在 `build/mesh-feasibility/`。本次运行没有连接到 ADB 安卓设备，没有执行无线硬件验证，不提供虚假的热点、蓝牙、Wi-Fi Direct 成功标记。

## 三类连接的选择

| 连接 | Android 10+ 可行性 | 建链中的角色 | 建议 |
| --- | --- | --- | --- |
| 同一手机热点或普通 Wi-Fi + NSD/TCP | 已有实现可复用；无线兼容性需真机核对 | 热点提供网络接入；每台应用均接受和发起连接 | 第一优先，验证热点客户端互通、多播发现和断线重入 |
| 经典蓝牙 RFCOMM | Android 提供双向流接口，适合体积较小的账目 | 本次连接有监听方和发起方，每台都可以承担两种职责 | 与热点方案并行优先，使用安全配对，失败保留待同步数据 |
| Wi-Fi Direct | Android 有原生 P2P API，不用用户预先连接热点；设备需支持 | 系统仍选 Group Owner，这不是主账本 | 后续增加，核对连接建立、GO 离开后重组、与已有 Wi-Fi 并存 |
| Wi-Fi Aware | API 26+，但硬件、固件及当时可用状态不统一 | NAN 由系统组网 | 可选增强，不能作为覆盖所有 Android 10+ 机型的唯一通道 |

Android 官方明确 Wi-Fi Direct 无需接入网络或热点，但仍有 Group Owner；经典蓝牙也需要监听和发起连接。产品可以保证**业务副本对等、任何人能录入、没有唯一主账本**，不能把无线连接协议中的角色一并宣称不存在。

Google Nearby Connections 的 Cluster 是可研究的 M-to-N 方案，但 Android 版本使用 Google Play services SDK。当前项目只依赖现有 Android 工具，不宜把这类额外依赖设成唯一底座；是否采用需要另行验证目标手机环境。

Android 10/11 的扫描可能需要位置权限及系统位置开关；Android 12+ 蓝牙扫描、广播和连接采用附近设备相关运行时权限；Android 13+ 的 Wi-Fi Direct 还需处理附近 Wi-Fi 权限。权限要按链路和系统版本请求，拒绝一个权限后仍保留离线记账和其他可用通道。仅有“Android 10+”不能证明某台手机支持 Wi-Fi Aware 或某种并发无线组合。

## 推荐目标结构

```mermaid
flowchart LR
    A[安卓甲：完整本地副本] <-->|热点 TCP／Wi-Fi Direct／蓝牙| B[安卓乙：完整本地副本]
    B <-->|有连接时交换缺失记录| C[未来同行丙：完整本地副本]
```

这是应用层的传播关系，不声称两条无线链路可在任何机型上同时存在。乙可先收甲的记录，稍后再传丙；各端只有在形成连接或被同行携带记录后才能补齐。mesh 不会突破无线距离限制。不同城市、不同 Wi-Fi 且无法近距离连接时，仍需要双方可达的互联网中转或之后再相遇。

建议拆分为四层：

1. **本地账本**：先持久写入，再触发同步。成员使用固定 memberId；设备有单独 deviceId，显示名字不作为身份键。两个人的旅行是多成员结构的特例。
2. **合并与结算**：操作 ID 去重；支出保存当时的付款人和明确分摊金额，后来加人不重分旧账。删除使用保留的删除记录。时间用于展示，不用手机时间大小决定哪条账目获胜。
3. **对等同步**：握手确认旅行、协议版本和授权；比较摘要，分批请求缺失操作；数据库提交后确认接收。记录可从其他已加入旅行的设备转发，不要求原作者在线。
4. **连接适配器**：热点 TCP、蓝牙 RFCOMM、Wi-Fi Direct 共用同一套同步协议。优先复用已可用连接，失败时切换通道；同一记录多路到达仍只生效一次。扫描、连接数、重试和定期校准均设上限，先保证前台同步。

v1 仍把成员写死为 a/b，使用 shareA 和 B 欠 A 的单一余额；云端另有每旅行 8 个设备快照的上限。多人 v2 需同步改造 SQLite、邀请码、成员身份、分摊、结算、记录与云端模型，并明确阻止旧客户端误读多人旅行。先备份、再迁移；两人旧旅行可映射为两个固定成员 ID。成员邀请和权限是独立问题，不因为有热点或没有主账本而自动解决。

## 下一阶段真机验收

当前尚未实现新的安卓蓝牙/Wi-Fi Direct 产品适配器。建议先将共享帧与合并逻辑从 `LanSync` 的 TCP 连接管理中拆出，再做热点与蓝牙双通道，Wi-Fi Direct 作为下一条可选路径；纯无线 mesh 留在相同操作日志之上扩展。

先准备两台真实安卓手机，在 Android 10/11、12/13 和后续版本上逐步覆盖；两台手机的一次测试不能代表所有厂商均兼容。验收时至少核对：

- 双方各离线记账，应用重开后通过热点交换；无互联网时可用。
- 热点提供者退出：各端记录保留，换任意人的热点后补齐，不声称原 Wi-Fi 网络还能维持。
- 不开热点时，经安全蓝牙配对交换缺失记录；拒绝权限、取消配对和断连后可恢复。
- 切换链路、两条链路重复到达、请求发出但回执丢失均不重复入账。
- Wi-Fi Direct 双方可发现和建链，GO 退出后可重新建链；该结果不能当作已实现多跳 mesh。
- 第三台设备加入时再验收 A—B—C 接力、环路去重、多个成员录入和结算，并检验同一人多设备的身份映射。

真机无线测试及首次与再次同步的耗时、流量、功耗尚无结果，应在完成适配器后测量，再决定默认选路与重试间隔。
